# OFRL-IB-001 — Engineering Architecture

**Architecture version:** 0.4.0  
**Status:** Approved for V1 engineering baseline; dependency adoption remains gated by proof-of-concept  
**Implementation language:** Rust  
**Baseline date:** 2026-11-04

## 1. Engineering direction

Rust is the implementation language for the financial calculation engine, authoritative validation logic, and command-line tooling.

The Rust implementation is the canonical source of financial calculations. The Excel workbook is an analyst-facing reporting and interoperability artifact generated from canonical Rust outputs. It must not introduce a second, independently maintained set of calculation rules.

Other tools may be used for a specific task such as data inspection, independent comparison, or file interoperability. They must support the research rather than create competing calculation engines.

The initial architecture is intentionally small: one domain/model library crate and one CLI crate in a Cargo workspace. Additional crates should be extracted only when a stable boundary and independent reuse case exist.

## 2. Logical architecture

**Input schema → Parsing → Domain validation → Domain model → Forecasts and schedules → Financial statements → Integrity checks → Output adapters**

| Layer | Responsibility | Design constraint |
|---|---|---|
| Domain | Money, rates, days, periods, assumptions, balances, currency/unit metadata | Strong types; no spreadsheet or file-format dependency |
| Parsing | Versioned JSON/CSV input contract | Strict parsing; decimal monetary values arrive as strings |
| Validation | Input domains and cross-field constraints | Typed errors; no silent coercion |
| Forecast | Revenue and operating forecast | Deterministic calculation functions |
| Schedules | Working capital, PP&E, debt, tax, dividends | Explicit opening and closing roll-forwards |
| Statements | Income Statement, Balance Sheet, Cash Flow Statement | Derived from the same domain model |
| Integrity | Accounting identities, schedule invariants, funding feasibility | Separate hard gates and warnings |
| Output adapters | Canonical JSON/CSV and XLSX report | Preserve canonical decimal strings outside Excel's numeric representation |
| CLI | Run, validate, export, report | Thin orchestration layer; no financial logic hidden in CLI |

The domain and calculation layers must remain independent of Excel, operating-system paths, and network clients.

## 4. Numeric policy

The authoritative calculation layer must not use binary floating-point for monetary values.

rust_decimal is the initial fixed-point candidate, not yet an adopted dependency. Current upstream documentation describes a 96-bit mantissa with a scale from 0 to 28, giving approximately 28–29 significant decimal digits. This is finite fixed precision: it is not arbitrary precision and it does not represent every rational number exactly.

The proof-of-concept must test the actual OFRL input envelope, including large balances, small fractional amounts, percentage calculations, division by 365, and non-terminating division.

Required arithmetic policy:

- Use checked operations for additions, subtractions, multiplications, and divisions that may exceed the supported numeric domain.
- Convert None from checked arithmetic into an explicit typed model error.
- Do not use saturating operations or replace overflow with zero.
- Do not apply application-level quantization/rounding within schedules.
- Recognize that fixed-precision division can produce a bounded-scale result; document the crate's actual behaviour and effective scale from the proof-of-concept.
- Define the final rounding mode and display scale at an explicit reporting boundary.
- Keep canonical Decimal values as decimal strings in JSON/CSV.
- Preserve currency, unit, scale, period, schema version, and model version metadata.
- Do not claim unlimited precision, exact rational arithmetic, or "no rounding" where a division is not exactly representable.

For canonical JSON fields, test an explicit Serde string representation such as rust_decimal::serde::str. Do not depend on a global serializer default that may emit JSON numeric tokens.

### Numeric proof-of-concept evidence (2026-11-04)

The isolated Decimal/JSON/CSV POC is recorded at:

- [POC source and test scope](poc/decimal-contract/README.md)
- [Dependency and MSRV review](poc/decimal-contract/DEPENDENCY_REVIEW.md)
- [JSON Schema](../../schemas/ofrl-ib-001-amount-record-0.1.0.schema.json)

The PR #6 head commit passed formatting, Clippy, 9 unit tests, and documentation generation on Rust 1.85.0 and Rust 1.99.1. The tested division outputs at Decimal scale 28 were:

- 1 / 365 = 0.0027397260273972602739726027
- 1 / 3 = 0.3333333333333333333333333333
- (1 / 3) × 3 = 0.9999999999999999999999999999

The tests also exposed a raw-parser input hazard for a 29-fractional-digit string. The POC's Serde boundary now rejects scale above 28 and requires exact parse-to-string round-trip before accepting input. This is a required boundary control for the selected candidate.

**POC conclusion:** the current Decimal-string interchange approach passes its defined test scope. rust_decimal 1.43.0 remains a candidate, not an approved final engine dependency. The full transitive dependency inventory/SBOM, lockfile policy, security review, model-specific numeric envelope, calculation error analysis, and XLSX reconciliation remain open. POC success does not establish three-statement model correctness.

Cross-field semantic validation remains a separate Rust implementation gate; passing JSON Schema alone does not validate accounting identities, period continuity, or statement roll-forwards.

## 5. Candidate Rust ecosystem components

Dependencies remain candidates until their proof-of-concept, complete dependency review, and model-specific acceptance tests are complete. See [the POC dependency review](poc/decimal-contract/DEPENDENCY_REVIEW.md) for the current evidence and open gates.

| Component | Candidate | Intended role | Adoption condition |
|---|---|---|---|
| Fixed-point decimal | rust_decimal (POC baseline: 1.43.0) | Financial amounts and fixed-point model parameters | Pass range, scale, checked-operation, division, and serialization tests |
| Serialization | serde | Typed input/output schemas | Explicit Decimal-string representation and stable schema tests |
| JSON | serde_json | Canonical JSON interchange | Reject numeric tokens for Decimal fields; stable schema contract |
| CSV | csv + Serde | Tabular input/output interchange | Decimal-string round-trip and strict header/column tests |
| XLSX export | rust_xlsxwriter | Generate analyst-facing .xlsx reports | Confirm formatting, formula policy, output precision, and compatibility |
| Property testing | proptest | Generate inputs and test invariants | Bounded strategies, reproducible cases, and useful shrinking |
| Error handling | Standard Result, with a reviewed error crate if justified | Explicit failure surfaces | Stable and actionable domain errors |

Do not select dependencies solely because they are popular or newly released. Record the exact versions, features, MSRV, licence, maintenance and security posture, and relevant transitive dependencies.

### Decimal serialization boundary

Use field-level string serialization for canonical Decimal fields. The expected JSON form is a quoted decimal string, for example:

~~~json
{"revenue":"123456.7800"}
~~~

The parser should reject an unquoted numeric token for a Decimal field. This prevents a JSON consumer from first converting an amount to binary floating-point and losing precision before the model receives it.

CSV files should use canonical headers, documented row semantics, and decimal text fields. CSV has no intrinsic type system; the schema and parser must provide the type contract.

### Excel export boundary

Excel stores numeric cell values as IEEE 754 binary floating-point values with approximately 15 significant decimal digits. The optional rust_decimal integration in rust_xlsxwriter only writes a Decimal when it can be represented as f64.

Therefore:

- Canonical outputs remain available in decimal-string JSON/CSV.
- XLSX is a presentation artifact with a declared display scale and tolerance.
- Values beyond the workbook's declared numeric precision must not be silently presented as exact.
- Workbook exports must be reconciled period-by-period against canonical Rust outputs.
- Any displayed value rounded for presentation must retain access to its canonical source value.
- Excel formulas must not replace the Rust calculation engine in V1.

calamine may be considered later if importing existing Excel or OpenDocument files becomes a real requirement. XLSX input is not required in V1.

## 6. API and error design

The calculation library should expose deterministic functions with explicit inputs and outputs.

- Prefer immutable input structures and pure calculation functions.
- Use newtypes for semantically different quantities such as Money, Rate, Days, and Period.
- Encode currency and display scale as explicit metadata; never infer them from a formatted string.
- Use enums for period types, validation severity, and model status where appropriate.
- Return typed Result values for invalid inputs and arithmetic failures.
- Distinguish invalid inputs from valid but unfavourable economic outcomes.
- A negative forecast cash balance is a valid calculated outcome. It fails the funding-feasibility gate, but it is not an arithmetic exception.
- Keep financial calculations independent of command-line parsing and workbook generation.
- Avoid global mutable state and hidden configuration.

## 7. Testing and validation

The Rust test suite should include:

1. **Unit tests:** individual financial formulas and schedule roll-forwards.
2. **Integration tests:** complete statements and cross-statement reconciliation.
3. **Property-based tests:** invariants over generated valid inputs, with shrinking to minimal failing examples.
4. **Golden tests:** deterministic synthetic scenarios with reviewed expected outputs.
5. **Boundary tests:** zero denominators, extreme-but-valid inputs, negative earnings, and invalid domains.
6. **Serialization tests:** JSON and CSV Decimal strings round-trip without precision loss; numeric JSON tokens are rejected.
7. **Numeric-limit tests:** Decimal minimum/maximum range, scale behaviour, checked overflow, underflow, and division-by-zero.
8. **Division tests:** terminating and non-terminating quotients, including 1 / 365, with effective scale and result recorded.
9. **Export tests:** workbook structure, required sheets, labels, declared display precision, and comparison with canonical outputs.

Property-test generators must respect the model's input domains. Separate invalid-input tests must verify that rejected values produce explicit errors.

## 8. Development checks

Proposed baseline commands after the Cargo workspace exists:

~~~bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets
cargo doc --workspace --no-deps
~~~

The exact feature matrix and CI commands should be fixed with the initial implementation. Commit Cargo.lock for reproducible application builds. CI should use least-privilege token permissions and a pinned runner image/toolchain policy.

Passing compilation, formatting, Clippy, or unit tests does not by itself establish financial correctness. Accounting and cross-statement invariants remain separate mandatory acceptance gates.

## 9. Dependency review

Before adopting a crate, record:

- Purpose and exact feature set.
- Current version and minimum supported Rust version (MSRV).
- Licence and compatibility with OFRL's licensing policy.
- Maintenance status, release history, security advisories, and transitive dependencies.
- Whether a smaller standard-library implementation would be preferable.
- Known precision, performance, portability, and interoperability limitations.

Do not select a dependency solely because it is popular or newly released. The version used by a proof-of-concept is a tested candidate, not a perpetual endorsement; check upstream status again before a production release.

## 10. Delivery stages

| Stage | Deliverable | Exit condition |
|---|---|---|
| A — Specification | Financial rules, schemas, engineering architecture, validation matrix | V1 baseline decisions recorded |
| B — Numeric and schema proof of concept | Decimal checks, JSON/CSV round-trip, input validation | Precision and range behaviour documented; all POC tests pass |
| C — Calculation library | Forecasts, schedules, statements, validation | Unit, integration, property, and golden tests pass |
| D — Deterministic CLI | Run and validate a synthetic scenario | Same model version and inputs reproduce the same canonical outputs |
| E — Excel report | Analyst-facing workbook | Workbook reconciles to canonical outputs within declared display tolerance |
| F — Hardening | Property, boundary, golden, export tests; documentation | Release gates pass or failures are disclosed |
| G — Reusable components | Extract abstractions that have value beyond this project | Stable API, documentation, tests, licence, and review |

Do not publish a general-purpose crate merely to create a crates.io presence. Release a component when it has a stable purpose, a useful API, meaningful tests, documentation, and a likely audience beyond this project.
