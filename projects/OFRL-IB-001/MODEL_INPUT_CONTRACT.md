# OFRL-IB-001 — Model Input Contract

**Contract version:** 0.1.0  
**Status:** Proposed for V1 implementation  
**Owner:** OFRL-IB-001  
**Canonical format:** Versioned JSON with decimal-string numeric fields

## 1. Purpose

This document defines the complete external input boundary for the first integrated three-statement model. It is intended to be stable enough for a Rust domain model, deterministic fixtures, automated validation, and future non-Rust consumers.

The input contract is not a workbook layout. It separates historical source statements, model metadata, and forecast assumptions. Calculation outputs are generated by the engine and must not be accepted as user-supplied forecast results.

The machine-readable schema is:

[ofrl-ib-001-model-input-0.1.0.schema.json](../../schemas/ofrl-ib-001-model-input-0.1.0.schema.json)

## 2. Contract principles

1. **Version explicitly.** Every payload declares schema_version. Unknown versions are rejected.
2. **Reject unknown fields.** Each object uses a closed field set to catch misspellings and unreviewed additions.
3. **Use decimal strings.** Monetary amounts, ratios, percentages, and day metrics are strings. JSON number tokens are not accepted for these fields.
4. **Use one model currency and scale.** Every monetary value in one model instance uses the model-level reporting currency and unit_scale.
5. **Separate source from assumption.** Historical statement values are source inputs; forecast drivers are assumptions; forecast statements are calculated outputs.
6. **Preserve history.** The model receives the opening Balance Sheet before the first historical year, allowing period-by-period roll-forward validation.
7. **Validate semantics separately.** JSON Schema validates structure and lexical constraints. Cross-field accounting and period checks are performed by the model validator.
8. **Do not repair invalid input silently.** No missing monetary field is defaulted to zero, no currency is inferred, and no balancing plug is inserted.

## 3. Top-level payload

The payload contains:

| Field | Meaning |
|---|---|
| schema_version | Input schema version; V1 schema uses 0.1.0 |
| model | Model identifier, reporting currency, unit scale, and day-count basis |
| opening_balance_sheet | Opening balances immediately before the first historical period |
| historical_periods | Exactly three annual historical periods |
| forecast_periods | Exactly five annual forecast periods |

The top-level contract rejects additional fields. New material fields require a schema version change or an explicitly compatible extension policy.

## 4. Model metadata

The model object contains:

- model_id: stable identifier for the model instance.
- model_name: human-readable name.
- reporting_currency: three uppercase letters, e.g. USD or THB. The schema checks syntax; the runtime must check the supported currency registry if a formal ISO 4217 guarantee is required.
- unit_scale: units, thousands, or millions. This applies to every monetary amount in the payload.
- day_count_basis: fixed at 365 for the V1 working-capital day calculations.

The model must not mix currencies or unit scales within one calculation. Currency conversion is outside V1.

## 5. Opening Balance Sheet

opening_balance_sheet is the closing position immediately before the first historical period begins. It includes:

- as_of_date
- cash
- accounts_receivable
- inventory
- gross_ppe
- accumulated_depreciation
- accounts_payable
- interest_bearing_debt
- share_capital
- retained_earnings

The opening position is required because the first historical year's working-capital, PP&E, debt, cash, and retained-earnings movements cannot be reconciled from closing balances alone.

Opening balance values use the model's reporting currency and unit_scale. Retained earnings may be negative; the other listed opening balances are non-negative in V1.

## 6. Historical periods

The historical_periods array contains exactly three ordered annual periods. Each period includes:

- period_id, start_date, and end_date.
- source classification and optional source reference.
- income_statement.
- balance_sheet.
- cash_flow_statement.

### 6.1 Historical Income Statement

| Field | Domain | Meaning |
|---|---|---|
| revenue | Non-negative amount | Revenue |
| cogs | Non-negative amount | Cost of goods sold; excludes depreciation |
| operating_expenses | Non-negative amount | Operating expenses; excludes depreciation, interest, and tax |
| depreciation | Non-negative amount | Depreciation expense |
| interest_expense | Non-negative amount | Interest expense |
| income_tax_expense | Non-negative amount | Income tax expense |
| net_income | Signed amount | Reported/normalized net income; checked against the V1 calculation |

V1 does not include other income, other expenses, discontinued operations, non-controlling interests, or other comprehensive income. A source statement containing those material items must be normalized transparently or excluded; it must not be silently forced into the simplified model.

### 6.2 Historical Balance Sheet

| Field | Domain | Meaning |
|---|---|---|
| cash | Non-negative amount | Cash and cash equivalents in the V1 scope |
| accounts_receivable | Non-negative amount | Trade receivables |
| inventory | Non-negative amount | Operating inventory |
| gross_ppe | Non-negative amount | Aggregate gross PP&E |
| accumulated_depreciation | Non-negative amount | Aggregate accumulated depreciation |
| accounts_payable | Non-negative amount | Trade payables |
| interest_bearing_debt | Non-negative amount | Interest-bearing debt |
| share_capital | Non-negative amount | Share capital |
| retained_earnings | Signed amount | Retained earnings, which may be negative |

Net PP&E is derived as gross_ppe less accumulated_depreciation. Total assets, liabilities, and equity are derived by the model; users do not enter a balancing total.

### 6.3 Historical Cash Flow Statement

The normalized historical Cash Flow Statement contains:

- net_income
- depreciation_addback
- change_in_operating_nwc
- cash_from_operations
- capex
- cash_from_investing
- debt_drawdowns
- principal_repayments
- dividends
- cash_from_financing
- net_change_in_cash
- opening_cash
- closing_cash

The V1 normalized historical structure intentionally excludes other cash-flow adjustments and other investing/financing categories. Where a source statement contains them, normalization must be documented and the source amounts must not be silently discarded.

The opening_cash must equal the opening Balance Sheet cash for the first historical period, and the prior historical Balance Sheet cash for later periods.

## 7. Forecast periods

The forecast_periods array contains exactly five ordered annual periods. Each forecast period contains period_id, start_date, end_date, and an assumptions object.

Every forecast period must provide all assumptions explicitly:

| Field | Representation | Domain |
|---|---|---|
| revenue_growth | Signed decimal ratio | Greater than or equal to -1.0 |
| cogs_pct_revenue | Non-negative decimal ratio | No 100% cap; loss-making gross margin is valid |
| operating_expenses_pct_revenue | Non-negative decimal ratio | No 100% cap |
| dso | Non-negative decimal days | Days sales outstanding |
| dio | Non-negative decimal days | Days inventory outstanding |
| dpo | Non-negative decimal days | Days payable outstanding |
| capex_pct_revenue | Non-negative decimal ratio | Capital expenditure as a share of revenue |
| depreciation_rate | Decimal ratio | 0.0 to 1.0 inclusive |
| debt_drawdowns | Non-negative amount | Explicit debt drawdown assumption |
| principal_repayments | Non-negative amount | Must not exceed opening debt plus drawdowns |
| interest_rate | Non-negative decimal ratio | Annual interest rate |
| tax_rate | Decimal ratio | 0.0 to 1.0 inclusive |
| dividend_payout_ratio | Decimal ratio | 0.0 to 1.0 inclusive |

All rate and percentage values are stored as ratios, not percentage points. For example, the string 0.20 means 20%, not 0.20%.

Days are decimal strings. Fractional day values are permitted. The model uses the metadata day_count_basis of 365 when converting days into forecast balances.

## 8. Period rules and semantic validation

The JSON Schema checks array lengths, field formats, and basic lexical properties. Runtime semantic validation must additionally enforce:

1. Exactly three historical and five forecast periods.
2. Every period_id is unique.
3. Periods are ordered chronologically and do not overlap.
4. Each period is an annual reporting period under the declared fiscal calendar.
5. Period dates are valid, start_date is not after end_date, and adjacent periods are contiguous.
6. The first historical period begins immediately after opening_balance_sheet.as_of_date.
7. The first forecast period begins immediately after the last historical period ends.
8. Period identifiers agree with the declared fiscal-year convention.
9. All monetary amounts use the model-level reporting currency and unit_scale.
10. All decimal strings are exactly representable by the selected Decimal candidate.

The day_count_basis is a model convention for DSO/DIO/DPO calculations; it is not a requirement that every annual fiscal period contain exactly 365 calendar days.

## 9. Historical accounting and roll-forward validation

For every historical period, the model must validate:

### Income Statement

net_income = revenue − cogs − operating_expenses − depreciation − interest_expense − income_tax_expense

### Balance Sheet

net_ppe = gross_ppe − accumulated_depreciation

total_assets = cash + accounts_receivable + inventory + net_ppe

total_liabilities = accounts_payable + interest_bearing_debt

total_equity = share_capital + retained_earnings

total_assets = total_liabilities + total_equity

### Cash Flow Statement

net_income agrees with the Income Statement.

depreciation_addback agrees with Income Statement depreciation.

change_in_operating_nwc agrees with the movement in operating net working capital from the prior Balance Sheet.

cash_from_operations = net_income + depreciation_addback − change_in_operating_nwc

cash_from_investing = −capex

cash_from_financing = debt_drawdowns − principal_repayments − dividends

net_change_in_cash = cash_from_operations + cash_from_investing + cash_from_financing

closing_cash = opening_cash + net_change_in_cash

closing_cash agrees with Balance Sheet cash.

### Historical schedule roll-forwards

Under the V1 no-disposal/no-revaluation simplification:

- gross PP&E closing = gross PP&E opening + CapEx.
- accumulated depreciation closing = accumulated depreciation opening + depreciation.
- debt closing = debt opening + debt drawdowns − principal repayments.
- retained earnings closing = retained earnings opening + net income − dividends.
- share capital remains unchanged.

These rules are specific to the synthetic/normalized V1 model. They are not a statement that real-world financial statements universally have no disposals or other adjustments.

## 10. Forecast calculation boundary

Forecast statements and schedules are calculated by the Rust engine from the last historical closing balances and the forecast assumptions. The input payload must not contain forecast financial statements or computed closing balances.

The engine must return both canonical decimal-string outputs and validation findings. Negative closing cash is a valid calculated result that fails the Scenario Feasibility gate; it is not silently converted into debt or equity financing.

## 11. Schema versus runtime responsibility

| Concern | JSON Schema | Runtime semantic validator |
|---|---:|---:|
| Required fields and unknown-field rejection | Yes | Defensive check |
| Decimal string lexical grammar and max fractional scale | Yes | Yes, including exact representability and Decimal range |
| Currency syntax | Yes | Supported-code policy if enabled |
| Array length and basic date syntax | Yes | Yes |
| Period uniqueness/order/contiguity | No | Yes |
| Currency/unit consistency | Model-level metadata | Yes |
| Historical statement identities | No | Yes |
| Cross-statement reconciliations | No | Yes |
| Forecast assumption numerical bounds | Some lexical/domain shape | Yes, numeric comparisons |
| Debt repayment not exceeding available debt | No | Yes |
| Scenario Feasibility | No | After calculation |
| Decimal overflow/underflow | No | During calculation |

JSON Schema validation is necessary but not sufficient to authorize a model run.

## 12. Versioning and compatibility

Changes that alter field names, required fields, units, signs, calculation meaning, period semantics, or validation rules require a schema version change and migration notes.

Additive optional fields may be considered compatible only if unknown-field behavior, consumers, and versioning policy remain explicit. V1 rejects undeclared fields to avoid silent drift.

## 13. Current status

The machine-readable input schema and synthetic payload are design-stage artifacts. They must be validated by a Draft 2020-12 validator and exercised by automated valid/invalid fixture tests before they are treated as implementation-ready. The POC Decimal parser validates only the amount field boundary; it is not the full model input validator.
